# Сервисы обучения и рекомендаций

Точка входа: `createLearningServices(db, options?)` из `src/services/index.ts`.
Фабрика возвращает `profiles, recommendations, fsrs, study`; импорт не запускает
бота и не подключается к рабочей базе. Все операции принимают внутренний
`userId`, полученный обработчиком из Telegram-контекста.

```ts
import { db } from "../src/config/connection";
import { createLearningServices } from "../src/services";
import { Rating } from "ts-fsrs";

const services = createLearningServices(db, {
  frequencySource: "your-corpus-version", // значение frequencySource в словаре
});
await services.profiles.configure(userId, {
  selfReportedCefrLevelId: a1LevelId,
  timezone: "Europe/Moscow",
  dailyNewMeaningLimit: 10,
});

const step = await services.study.next(userId);
if (step.kind === "new" || step.kind === "review") {
  // Сохрани step.card на сервере вместе с выданным вопросом.
  // После ответа используй тот же снимок, в том числе при повторном callback.
  const result = await services.fsrs.answer(
    userId, step.card.wordMeaningId, Rating.Good, step.card,
  );
}
```

Обработчики Telegram и отправка сообщений остаются в слое бота.
Сервисы полностью реализуют выбор и изменение состояния; `src/index.ts`
по-прежнему содержит исходные обработчики-заглушки.

## Как выбирается следующий шаг

`study.next(userId, at?)` возвращает discriminated union:

| kind | Содержание |
| --- | --- |
| review | Просроченная Learning/Review/Relearning-карточка, значение и preview |
| new | Уже добавленная New-карточка, значение и preview |
| recommendation | Ещё не показанное предложение, полное значение |
| idle | Причина отсутствия предложения и nextDueAt, если есть будущая карточка |

Просроченные карточки выбираются по `due, id`, а не по частотности слова.
Их due уже рассчитано FSRS с учётом памяти конкретного пользователя.
Перед новым предложением сервис выбирает уже принятые New-карточки.
Лимит новых значений не мешает продолжать обучение уже добавленных карточек.
Будущие карточки не предлагаются для досрочного повторения.

Для новых слов сервис сначала повторно проверяет подготовленные непоказанные
предложения. Учитываются актуальный диапазон сложности, предпочтения, cooldown,
дневной лимит и нагрузка; изменение заявленного уровня не оставляет в очереди
прежние слишком сложные предложения. Если пригодных предложений нет,
создаётся пачка до 10 значений и возвращается её первое предложение.
Чтение следующего шага не устанавливает shownAt.

`idle.reason`: `daily_limit`, `reviews_overloaded` или `no_candidates`.
`nextDueAt` — ближайшая будущая дата среди карточек с памятью и New-карточек.

## Словарный профиль

`profiles.configure(userId, patch, at?)` принимает:

- `selfReportedCefrLevelId`: существующий CEFR id или null;
- `timezone`: IANA-зону, проверяемую через Intl;
- `dailyNewMeaningLimit`: неотрицательное целое;
- `explorationRate`: число от 0 до 1.

После изменения настроек оценки пересчитываются.
CEFR задаёт prior (-2, -1, 0, 1, 2, 3), а не порядок id из БД.

`profiles.assess(userId, wordMeaningId, answer, at?)` принимает
`{ knewBefore, source, answerNotRevealed: true }`.
Вызывай до раскрытия перевода/подсказки. Правильный первый ответ атомарно
создаёт наблюдение и known-предпочтение, без карточки FSRS.
Неправильный ответ не добавляет слово в обучение.
Повтор возвращает первое наблюдение; он не увеличивает вес свидетельств.

`profiles.rebuild(userId, at?)` читает всю историю первичных ответов
страницами и решает регуляризованную логистическую задачу из
[new-word-recommendations.md](new-word-recommendations.md).
Используются веса 1/0.25 для recognition_test/self_report и затухание с
периодом полураспада 90 дней. Оптимизация — метод Ньютона с решением
разреженной системы сопряжёнными градиентами и поиском шага.
Сложности и тематические веса берутся из первоначальных снимков.
Тематические поправки используются в выдаче только после 5 единиц веса.

Из FSRS читаются подходящие Review-события за 90 дней с точным интервалом
не менее суток. Берётся первое подходящее событие за локальный день и не
более 3 единиц веса на значение, с полураспадом 30 дней.
Hard/Good/Easy означают успешное припоминание; Again — неуспешное.
Из остатка вычитается ожидаемая вероятность, затем общая поправка пользователя.
Значения без тем входят в общую поправку. Для weakness нужны минимум
5 различных значений темы и тематический вес 10.

Метод возвращает профиль, prior, тематические профили, globalGap и Map
`weaknesses`. Вычисленные поля сохраняются атомарно; явные интересы и
блокировки сохраняются. Удалённые темы могут оставаться в неизменяемом JSON
старой проверки, но для них не создаются новые строки кеша.

Для первой версии пересчёт выполняется при каждом подборе новых слов:
сервис не использует потенциально устаревший кеш как источник истины.
При большом объёме истории можно добавить кеширование с инвалидированием;
сейчас важнее воспроизводимость расчёта из исходных наблюдений.

## Рекомендации

`recommendations.generate(userId, { count?, batchId?, at? })` возвращает
`{ batchId, status, recommendations }`.
По умолчанию count=10, максимум 500; фактическое число ограничено остатком
дневного лимита и словарём. Весь доступный пул читается страницами,
поэтому первые 500 id не получают преимущества.

Порядок алгоритма:

1. Пересчитать профиль и дневную нагрузку.
2. Применить ограничения FSRS, known/ignored/snoozed, блокировок и cooldown.
3. Рассчитать индивидуальную способность с тематическими поправками.
4. Оставить диапазон b около способности ±1; до веса проверок 10 действует
   потолок заявленного CEFR. При пустом диапазоне допустимы ближайшие более
   простые значения, затем ближайший A1 для способности ниже словаря.
5. Рассчитать соответствие уровню, частотность, интерес, слабую тему и
   штраф тематической нагрузки по формуле content-v1.
6. Собрать пачку без повторов wordId, с основной темой не более 40% для
   пачек от 5 значений. При нехватке кандидатов ослабляется только эта квота.
7. На каждой позиции применить epsilon-greedy и сохранить полную вероятность
   выбранного элемента, включая случай выбора лучшего в случайной ветке.

Без частотности признак равен 0.5. Если указан `options.frequencySource`,
ранги используются только из этого корпуса. Без настройки источник
выбирается автоматически, если он один; при нескольких источниках все ранги
получают нейтральное значение. Ранги разных корпусов не сравниваются напрямую.

`status` бывает `generated, existing, daily_limit, reviews_overloaded,
no_candidates`. Переданный batchId делает создание идемпотентным:
повтор читает сохранившиеся неотвеченные строки той же выдачи.
Если она уже отвечена/истекла, массив может быть пустым.
Это чтение истории; перед новым показом всё равно нужен markShown.

`recommendations.next(userId, at?)` возвращает одно актуальное непоказанное
предложение и status. Его использует study.next.

`recommendations.markShown(userId, id, at?)` повторно проверяет текущую
допустимость и диапазон сложности. Возвращает строку с shownAt или undefined,
если новое предложение уже недопустимо. Повтор для уже показанной строки
возвращает исходную запись. Слой доставки вызывает этот метод при показе
и обрабатывает свои сетевые ошибки; сервис не отправляет Telegram-сообщения.

`recommendations.respond(userId, id, feedback, { at?, answerNotRevealed? })`
делегирует атомарные изменения репозиторию и сам рассчитывает границы
локального дня. accepted добавляет New-карточку; already_known создаёт known.
Наблюдение self_report создаётся только при явном answerNotRevealed=true.
skipped откладывает на 7 дней, too_difficult — на 30, not_interested скрывает.
Повтор реакции идемпотентен; другую реакцию после записанной сохранить нельзя.
Устаревшее already_known не может создать known рядом с активной карточкой.

## FSRS 6

`fsrs.getParameters(userId)` читает персональные параметры из
`user_settings[fsrs.parameters.v1]`, иначе использует параметры библиотеки.
Фабрика принимает `options.fsrsParameters` для общих defaults.

`fsrs.configure(userId, patch)` валидирует и сохраняет частичные настройки:
request_retention, maximum_interval, enable_fuzz, enable_short_term,
learning_steps, relearning_steps и w. FSRS 6 требует 21 конечный вес.
Нормализацию допустимых диапазонов весов выполняет ts-fsrs.
maximum_interval ограничен 1..36500 дней; retention — строго между 0 и 1.
Обучение весов оптимизатором не выполняется: можно передать готовые 21 вес.

```ts
await services.fsrs.configure(userId, {
  request_retention: 0.9,
  learning_steps: ["1m", "10m"],
  relearning_steps: ["10m"],
  enable_fuzz: true,
});
```

`fsrs.preview(userId, wordMeaningId, at?)` возвращает исходную карточку,
retrievability и варианты следующего срока для четырёх оценок.

`fsrs.answer(userId, wordMeaningId, rating, expectedCard, at?)`
вычисляет R на исходной карточке, вызывает scheduler.next и атомарно сохраняет
карточку и журнал. Сравнивается выданный снимок expectedCard, включая сроки,
память и счётчики. Повторный callback со старым снимком не превращается
во второй ответ. Отвечать до due, до предыдущего ответа или за чужую
карточку нельзя. Manual не принимается как оценка пользователя.

`fsrs.addMeaning(userId, wordMeaningId, at?)` — явное ручное добавление,
в том числе после known/ignored: атомарно убирает предпочтение и создаёт
New-карточку. Повтор сохраняет состояние уже существующей карточки.
Этот путь используется для явного выбора/импорта и не применяет квоту
рекомендаций; для обычного принятия предложения используй respond.

## Время, параллельные запросы и тестирование

`at` нужен для воспроизводимых запусков; без него используется clock.
`localDayBounds` ищет границы календарной даты в IANA-зоне, а не прибавляет
24 часа. Проверены обычные дни, 23/25-часовые дни, получасовой DST,
отсутствующая полночь и пропущенная календарная дата.

Один экземпляр createLearningServices сериализует изменения и генерацию
для одного userId. В разных процессах инварианты записи защищаются
транзакциями, уникальными ключами, повторной проверкой eligibility/квот
и сравнением снимка FSRS. Ошибки SQLITE_BUSY передаются вызывающему коду;
повторять нужно всю операцию, сохраняя batchId/expectedCard.

`options.clock` и `options.random` позволяют воспроизвести расчёт в тестах.
`npm run test:algorithms` проверяет математику и сервисы на настоящем libSQL
в памяти. `npm test` также проверяет модели, миграции и репозитории.
